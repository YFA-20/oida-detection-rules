# OIDA Detection Rules

Suricata rules that detect the **behaviour** of [OIDA](https://getoida.dev)
(`oida-ics`) while it assesses OT/ICS protocols.

OIDA is not detected by a port or a payload signature: it speaks the real
protocol. The rules therefore match the protocol operations OIDA performs, and
correlate several operations that belong to the same scan.

> These rules are for defensive monitoring of authorised assessments. OIDA can
> stop CPUs, write process values and extract credentials. Test only against
> systems you own or have written authorisation to assess.

Each protocol folder contains:

- a `README.md` with the OIDA capability map for that protocol;
- one subfolder per fingerprinted command, with its own `README.md`, Suricata
  rules, reference capture and output.

## Global rule set

[`oida_detection.rules`](oida_detection.rules) at the repository root is the
complete rule set: every protocol file concatenated, with a generated header.

- **26 rules**: 5 S7comm, 14 OPC UA, 7 KNXnet/IP.
- Generated by `make rules` from the per-protocol files. Do not edit it by
  hand; edit the protocol file and regenerate.
- The per-protocol files remain the source of truth:
  - [`s7comm/s7 -i/oida_s7_-i_detection.rules`](s7comm/s7%20-i/oida_s7_-i_detection.rules)
  - [`OPC-UA/get-endpoint/oida_opcua_get_endpoints.rules`](OPC-UA/get-endpoint/oida_opcua_get_endpoints.rules)
  - [`knx/gateway-scan/oida_knx_gateway_scan.rules`](knx/gateway-scan/oida_knx_gateway_scan.rules)
- SIDs are unique across the whole set. `make test` replays all reference
  captures through the global file.

## Protocol fingerprints

### Siemens S7comm — `oida s7 <IP> -i`

`-i` is an action: OIDA skips its generic discovery, scans rack/slot, then
reads identification data with four SZL operations and a CPU-status read.

| SID | Behaviour |
| --- | --- |
| `9999901` | SZL `0x0011` — all identification data |
| `9999902` | SZL `0x001C` — all components |
| `9999903` | SZL `0x001C` index `0x0001` — automation-system name |
| `9999905` | SZL `0x0131` — communication capabilities |
| `9999920` | correlation 4/4 — full S7 fingerprint |

The reference capture is
[`s7comm/s7 -i/oida_-i_snap7.pcapng`](s7comm/s7%20-i/oida_-i_snap7.pcapng).
See [`s7comm/s7 -i/README.md`](s7comm/s7%20-i/README.md) for the PDU sequence,
the per-rule match and the slot-scan logic.

### OPC UA — `oida opcua opc.tcp://<IP>:4840 --get-endpoints`

The OPC UA run is **two TCP connections**, not one:

| Phase | Connection | Security | Behaviour |
| --- | --- | --- | --- |
| A | new socket | **always `SecurityPolicy#None`** | `HEL/ACK`, `OPN`, `GetEndpoints` with a null session token, `CLO` |
| B | second socket | `None` by default, or `--policy/--mode` | `CreateSession`, `ActivateSession`, 10 `Read`, 2-3 `GetEndpoints`, `CloseSession`, `CLO` |

Phase A is OIDA's pre-auth discovery. It is created **before** `--policy` /
`--mode` are applied, so it is always a plaintext channel; it has no session
and its `GetEndpoints` is the operation that remains visible even when phase B
is encrypted.

Phase B reads BuildInfo (`ns=0;i=2260`) plus nine diagnostics/security nodes,
then calls `GetEndpoints` twice (certificate check, result count). The
`--get-endpoints` flag adds a third call for display. The three calls are
back-to-back and identical.

The client description carries the Python FreeOpcUa/asyncua defaults
(`urn:example.org:FreeOpcUa:opcua-asyncio`, `urn:freeopcua.github.io:client`,
`Pure Python Async Client`). The server-side ProductUri
`urn:freeopcua.github.io:python:server` and BuildInfo
`FreeOpcUa Python Server` belong to the **target** (the FreeOpcUa mock), not to
OIDA. OpalOPC is a C#/.NET scanner: OIDA references its check IDs, not its
stack. The full distinction is in
[`OPC-UA/get-endpoint/README.md`](OPC-UA/get-endpoint/README.md).

| SID | Behaviour |
| --- | --- |
| `9999930` | pre-auth `GetEndpoints`, no session (phase A) |
| `9999931` | `CreateSession` with FreeOpcUa/asyncua client identity |
| `9999932`-`9999941` | BuildInfo, nine diagnostics/security reads |
| `9999942` | 3 × `GetEndpoints` on the session |
| `9999950` | correlation — full OPC UA fingerprint |

The reference capture is
[`OPC-UA/get-endpoint/get-endpoints.pcapng`](OPC-UA/get-endpoint/get-endpoints.pcapng).
See [`OPC-UA/get-endpoint/README.md`](OPC-UA/get-endpoint/README.md) for the
secure-channel/session lifecycle, endpoint mapping, FreeOpcUa/asyncua
identification and limitations.

### KNXnet/IP — `oida knx <IP> -p 3671 --gateway-scan --tcp`

`--gateway-scan` opens a KNXnet/IP TCP tunnel, sweeps 255 individual addresses
with `A_DeviceDescriptor_Read` (APCI `0x0080`) inside TUNNELING_REQUEST frames,
queries the gateway with DESCRIPTION_REQUEST, and probes for gateways via
multicast SEARCH_REQUEST to 224.0.23.12. KNX has no encryption and no
authentication, so the whole sequence is plaintext on UDP/TCP 3671. UDP
tunneling is rejected on loopback/NAT'd targets, hence `--tcp`.

| SID | Behaviour |
| --- | --- |
| `9999960` | CONNECT_REQUEST (0x0205) on TCP/3671 — tunnel opened |
| `9999961` | TUNNELING_REQUEST (0x0420), cEMI L_Data.req, APCI `00 80` — one scan probe |
| `9999962` | >= 20 scan probes in 600 s from one source — bus sweep |
| `9999963` | SEARCH_REQUEST (0x0201) to multicast 224.0.23.12:3671 |
| `9999964` / `9999965` | DESCRIPTION_REQUEST (0x0203) on TCP / UDP 3671 — gateway info |
| `9999969` | correlation — TCP tunnel, probe burst on the same IP pair |

The reference capture is
[`knx/gateway-scan/oida_knx_gateway_scan.pcapng`](knx/gateway-scan/oida_knx_gateway_scan.pcapng)
(3256 packets on `lo`). See
[`knx/gateway-scan/README.md`](knx/gateway-scan/README.md) for the PDU
sequence, per-rule match, validation output and false-positive notes, and
[`knx/gateway-scan/attack_navigator_layer.json`](knx/gateway-scan/attack_navigator_layer.json)
for the MITRE ATT&CK for ICS Navigator layer (T0840, T0846, T0846.003, T0888).

## Design

Rules are built in two layers:

1. **Atomic indicators** — one rule per invariant protocol operation. Each rule
   sets an `xbits` flag with `track ip_pair` so the flag survives the
   short-lived TCP sessions OIDA opens during discovery. The expiry is
   protocol-specific (5 s for S7comm, 30 s for OPC UA, 60 s for KNX).
2. **Correlation** — one rule that fires only when all atomic indicators for the
   same IP pair are present inside the expiry window. This is what separates
   an OIDA fingerprint from an HMI or engineering station that happens to read
   the same object once.

Conventions:

- SID range `9999900`–`9999999`; SIDs are stable across revisions.
  - S7comm: `9999901`–`9999920`
  - OPC UA: `9999930`–`9999950`
  - KNXnet/IP: `9999960`–`9999969`
- `classtype:attempted-recon`; priorities 1 (correlated fingerprint), 2
  (dangerous operation), 3 (single recon request).
- Rules are `alert`-only by default. Tune to `drop` or add thresholds for your
  environment after baselining normal PLC traffic.

## Validate a rule set

Regenerate the global file after any protocol rule change:

```bash
make rules
```

Run the OPC UA reference capture through the global file:

```bash
suricata -r OPC-UA/get-endpoint/get-endpoints.pcapng \
  -S oida_detection.rules \
  -l /tmp/oida-opcua --runmode single -k none

grep -o '\[1:[0-9]*' /tmp/oida-opcua/fast.log | sed 's/\[1://' | sort -nu
```

Expected OPC UA SIDs:

```text
9999930 9999931 9999932 9999933 9999934 9999935 9999936 9999937
9999938 9999939 9999940 9999941 9999942 9999950
```

`9999950` is the correlation rule; it fires on the third
`GetEndpointsResponse`, after the last read and the third request.

Run the S7 reference capture through the same global file:

```bash
suricata -r "s7comm/s7 -i/oida_-i_snap7.pcapng" \
  -S oida_detection.rules \
  -l /tmp/oida-s7 --runmode single -k none

grep -o '\[1:[0-9]*' /tmp/oida-s7/fast.log | sed 's/\[1://' | sort -nu
```

Expected S7 SIDs: `9999901`, `9999902`, `9999903`, `9999905`, `9999920`
(repeated SZL requests produce several atomic alerts; five unique SIDs).

Or run all reference captures in one command:

```bash
make test
```

Run the KNX reference capture through the same global file:

```bash
suricata -r knx/gateway-scan/oida_knx_gateway_scan.pcapng \
  -S oida_detection.rules \
  -l /tmp/oida-knx --runmode single -k none

grep -o '\[1:[0-9]*' /tmp/oida-knx/fast.log | sed 's/\[1://' | sort -nu
```

Expected KNX SIDs: `9999960`, `9999961`, `9999962`, `9999965`, `9999969`
(`9999963` needs a capture that includes the multicast interface, and
`9999964` fires when the gateway description goes over TCP).

`make test-opcua`, `make test-s7` and `make test-knx` run one capture each.
The per-protocol
files can still be used alone with `-S`, for example:

```bash
suricata -r OPC-UA/get-endpoint/get-endpoints.pcapng \
  -S OPC-UA/get-endpoint/oida_opcua_get_endpoints.rules \
  -l /tmp/oida-opcua --runmode single -k none
```

## Adding a protocol

1. Capture one OIDA run against a lab device or mock service.
2. Extract the request sequence (`tshark -Y <protocol>` or the protocol
   dissector fields). Keep only operations that the command always performs.
3. Write one atomic rule per operation; anchor on the protocol header and the
   operation code, not on IP addresses or TCP ports alone.
4. Set a uniquely named `xbits` flag. Use `track ip_pair` when OIDA opens more
   than one TCP session per run.
5. Add a correlation rule that requires all flags; verify it fires on the
   capture, not only the atomic rules.
6. Add a protocol README documenting command, packet sequence, rule table and
   false-positive notes.
7. Add the new rule file to the `Makefile` `rules` recipe and regenerate
   `oida_detection.rules` with `make rules`.
